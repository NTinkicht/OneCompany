# OneCompany / CompanyOS — complete prioritized product, Work Units and verification

**Planning baseline:** 2026-10-18. **Product vision:** **One human; one governed AI-powered software company.** This is a **reusable product**, not a configuration dump or a Tabibi/Veritas-specific orchestrator. It takes an idea or existing application through requirements → plan → implementation → tests → independent review → merge → preview/release → operations → measured learning. A nontechnical user must be able to understand what is happening, what works, and what is blocked.

**Status:** Product-completion planning catalog; feature presence and tests are **not automatically verified**. Existing source of authority remains `.onecompany/{planning.json,portfolio.json,requirements-catalog.json,risk-register.json,queue.json,ledger.json,governance.json,...}` and the live GitHub evidence. This readable roadmap is **not** an implementation lease, a governance amendment, a release permit, or an alternative controller. Keep `docs/MASTER-EVOLUTION-ROADMAP-2026.md`, `docs/ROADMAP.md`, `docs/EXECUTION-CORE.md`, `docs/ONBOARDING.md`, `docs/engineering/*` and the capability register as detailed references.

## 1. Complete product experience

1. **Start:** describe a product or point OneCompany at an existing repo; see a read-only analysis of stack, dependencies, tests, security, permissions and compatibility.
2. **Decide:** edit a Product Brief, objectives, features, formal requirements, testable acceptance criteria, risks, milestones, constraints and priorities. Approval is explicit, not inferred.
3. **Build:** create and select dependency-ready bounded WUs, route among actually qualified actors, acquire an exclusive lease, implement via one branch/PR, run deterministic tests, review independently, repair and re-review, then merge through GitHub's protected policies.
4. **See it:** run real application/backend/database as applicable in a safe sandbox, preview it, inspect behavior, see true CI/product quality, blockers, budgets, audit and next WUs.
5. **Operate:** release only when authorized; monitor, recover, roll back, triage incidents and evaluate outcomes; safely re-plan. Support multiple separate projects without leaking target data or authority.

## 2. Ordering rules

- **P0:** working trustworthy autonomous engineering and safe first full-stack product path. Within each priority, the ID order is the proposed dependency sequence; independent scopes may advance in parallel after verified gates.
- **P1:** complete user-ready company product, integrated design/quality/operations and portfolio.
- **P2:** optional advanced integrations/scale, justified by benchmark and cost/license approval. Phase 3 operations appear in P1/P2 according to their risk.
- `VERIFY` = inspect exact code/CI/gate against criteria; `PLANNED` = roadmap only; `OPTIONAL` = not a dependency of first usable product.
- **Do not reactivate retired mechanisms:** old CAS control lease, four-controller hourly schedules, L4 authorization cycle, factory merge controllers, owner attestations, Mistral wake-bus review comments, sealed external review artifacts, cross-repo tokens or CodeRabbit blocking authority. Preserve the **simplified single hourly writer, independently approved exact-head GitHub bot review, native CI, review conversation resolution and GitHub auto-merge**. No AI self-approval/merge, forced merge or bypass of branch protection. If review cannot be verified, fail closed and report.

## 6. Exhaustive acceptance and test categories

- **Planning & contracts:** schema validity, objective/requirement/AC traceability, deterministic prioritization, graph cycles, dependency unlocks and approvals; satisfy `FR-001`, `NFR-001` and traceable extensions.
- **Concurrency & durability:** lease split-brain, duplicate PRs, resource lock/path conflicts, 100+ deterministic race seeds, CAS base/head changes, stop, crash, orphan, replay, journal corruption and stale generation.
- **GitHub exact-head governance:** `FR-002`, `FR-003`, `SEC-001`; off-scope file, untrusted review, self-review, stale SHA, unresolved conversations, missing CI, ruleset bypass attempts, reviewer outage. A comment is never equivalent to native approval.
- **Real actor/provider qualification:** read-only probe vs actual implementation, real authored code+tests, model failure classification, verified provider identity, zero implicit spend, no write tokens in prompts, provider quota/timeout/revocation, failover and recovery.
- **User journey and runnable application:** new and existing repo onboarding, explicit brief/approval, real full-stack CRUD/API/DB fixture, running HTTP + Playwright, expected revision and result, cleanup, rollback, truthful preview and Mission Control.
- **Security & privacy:** least privilege, repository/project isolation, prompt injection through untrusted files/PR comments, path traversal/symlink refusal, secret/PII leak, malicious tool call and spend/credential/production escalation refusal.
- **Product quality:** contract, API, DB integration, browser E2E, visual regression, keyboard/a11y, performance/load, source reproducibility and negative requirements; no blanket 100% coverage claim.
- **Operations:** availability/reliability, p95 and cost/outcome tracked against fixed benchmark; stop/restart, incident, staged rollback, restore, degraded service, multi-project concurrent work, retention and audit.

Every WU's `DONE` evidence: approved scope/AC, commit and test files, immutable run manifest, exact source head and relevant base, green required CI, real independent nonauthor current-head approval where required, conversations resolved, merged GitHub record, and runnable/staging/release evidence when applicable. Documentation-only WUs need objective docs consistency tests/review but do not claim runtime qualification.

## 7. Coverage governance and operating rules

1. **Reconcile, don't duplicate.** Search existing issues/PRs, main and `.onecompany/queue.json` for these proposed WUs. The queue is an execution baseline, and its `READY`/historical entries may not reflect live GitHub state; do not overwrite it wholesale or generate 40 simultaneous PRs.
2. **Approve scope before admission.** Convert outstanding approved product rows to versioned requirements, ACs, risks and bounded WUs via the existing schemas, with dependency graph, exact write scope, tests and issue link. A `PLANNED` row here is *not* ready to execute.
3. **No silent authority expansion.** Owner/legal/credential/spend/protected-governance/destructive production decisions require their documented authorizations; routine technical feature PRs use CI + independent AI review under real GitHub policies, not Kaporal159 or other standing human reviewer.
4. **Operate one canonical writer stream per WU.** Simplified Engineering :00 is the intended recurrent writer; no retired wake buses/controllers/merge scripts. Process a blocked GitHub write once more at smaller scope, then record exact operation, UAE timestamp and error; continue other WUs. Escalate owner action only on the same PR's third consecutive blocked run. Never disable the task from a blocked write.
5. **Release exit:** A first-time user can create/adopt a repo and complete a verifiably real app end-to-end, while repeated unattended WU cycles remain deterministic, review-independent, budget-contained and recoverable. P1 exit adds clear UI, full quality and multiple isolated projects. Optional P2 adapters remain truly optional.
