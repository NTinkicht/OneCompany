# Change Control

Every material change is evaluated for requirement, traceability, risk, architecture, test, documentation, deployment and rollback impact.

A scope or requirement change after implementation starts must record: what changed, why, source/authority, impacted IDs, risk delta, tests invalidated/added, architecture/data/API compatibility impact, documentation impact and whether the Work Unit must return to an earlier gate.

Evidence tied to superseded behaviour is stale. OneCompany prefers re-baselining explicitly over pretending the original plan still applies.
